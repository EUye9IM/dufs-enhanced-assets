Trust this server's certificate

You are seeing this page because the browser does not trust the certificate this dufs server uses, and the video player therefore runs without hardware decoding.

This server uses a private certificate authority that was generated on the server itself — no public CA is involved, and nothing leaves your network. For video playback to use WebCodecs (hardware decoding, the difference between realtime and a stuttering ~6 fps), the browser must consider the page a secure context. That only happens once the device trusts this CA.

Download CA certificate iOS / iPadOS profile

Both files contain the CA certificate only. Nothing secret is published here: the matching private key stays on the server.

"Proceed anyway" is not trust Clicking through the browser's warning only bypasses it for the current session, leaves the origin marked insecure, and has to be repeated. Installing the CA below is the only thing that actually changes the outcome.

Install the CA, once per device

iOS / iPadOS
  1. Tap iOS / iPadOS profile, then Allow when Safari asks to download the configuration profile.
  2. Open Settings — the profile appears as Profile Downloaded. Tap it, then Install (top right), enter the passcode, Install again. It is unsigned, so iOS will warn you about that — expected, it was generated next to this page.
  3. Required: Settings › General › About › Certificate Trust Settings, enable Root Certificate Full Trust for "dufs LAN root CA". Without this step the profile does nothing.
  4. Reload the file browser. There should be no certificate warning, and isSecureContext should be true.
Android
  1. Tap Download CA certificate.
  2. Settings › Security › More security settings › Encryption & credentials › Install a certificate › CA certificate, then pick the downloaded file. (Menu names vary by vendor; search the settings for "certificate".)
  3. Android will show a permanent "network may be monitored" notice — that is what installing a user CA means, and it is expected here.
  4. Chrome trusts user-installed CAs. Firefox for Android does not; use Chrome on Android.
macOS
  1. Download ca.crt, then double-click it to add it to the login keychain.
  2. Open Keychain Access, find "dufs LAN root CA", open it, expand Trust, and set When using this certificate to Always Trust.
  3. Or from a terminal: 
    sudo security add-trusted-cert -d -r trustRoot \
  -k /Library/Keychains/System.keychain ca.crt
Windows
  1. Download ca.crt.
  2. Run certmgr.msc → Trusted Root Certification Authorities → Certificates → right-click → All Tasks → Import → pick the file.
  3. Restart the browser. Importing into "Personal" instead of "Trusted Root" does not work.
Linux
  1. Download ca.crt.
  2. System store (Chrome/Edge/Safari-policy aware tools): 
    sudo cp ca.crt /usr/local/share/ca-certificates/dufs-lan.crt
sudo update-ca-certificates
  3. Chromium and Firefox on Linux read the NSS database instead: 
    certutil -d sql:"$HOME/.pki/nssdb" -A -t "C,," -n dufs-lan -i ca.crt
  4. Restart the browser afterwards — Chromium only reads the store at startup.
Firefox (any desktop OS)
  1. Firefox keeps its own trust store and ignores the system one.
  2. Settings › Privacy & Security › Certificates › View Certificates › Authorities › Import, pick ca.crt, and tick Trust this CA to identify websites.

Verify the certificate before trusting it

The first visit to this page necessarily travels over a connection that is not trusted yet, so in principle anyone on the path could have served a different CA. If that matters to you, compare the fingerprint printed by the server with the one you just downloaded. On the machine running dufs: 

openssl x509 -noout -fingerprint -sha256 -in assets/trust/ca.crt

It must equal the CA SHA-256 line printed by scripts/gen-tls.sh, and match the fingerprint shown by your device's certificate viewer.

If you would rather not install anything

Use http://localhost instead of a LAN IP — ssh -L 24601:localhost:24601 user@server and open http://localhost:24601. A loopback origin is already a secure context, so hardware decoding works with no certificate at all. It only helps for the machine holding the tunnel, though.
